---
title: Dify Premium on AWS
description: Deploy, customize, and upgrade Dify Premium on AWS
---

Dify Premium is our AWS AMI offering that allows custom branding and is one-click deployable to your AWS VPC as an EC2 instance. Head to [AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-t22mebxzwjhu6) to subscribe. It's useful in a couple of scenarios:

- You're looking to create one or a few applications as a small/medium business and you care about data residency.
- You are interested in [Dify Cloud](https://cloud.dify.ai), but your use case requires more resources than supported by the [plans](https://dify.ai/pricing).
- You'd like to run a POC before adopting Dify Enterprise within your organization.

## Access & Set up

After the AMI is deployed, access Dify via the instance's public IP found in the EC2 console (HTTP port 80 is used by default).

If this is your first time accessing Dify, enter the Admin initialization password (your EC2's instance ID) to start the setup process.

## Customize

### Configuration

Use Docker Compose 2.35.0 or later. Run `docker compose version` to check.

<Steps>
    <Step title="Edit Environment Variables">
        Edit environment variables in the relevant file on your EC2 instance:

        - **Essential startup values** live in `/dify/.env`. Edit them directly.

        - **Optional or provider-specific settings** have templates under `/dify/envs/`. Compose loads `.defaults` files automatically. If your local `.env` file already exists, edit it directly. Otherwise, copy the `.defaults` file to the local `.env` path named in its comments.

            For a service template ending in `.env.example`, drop the `.example` suffix instead. The `middleware.env.example` template belongs to the separate [source-code development workflow](/en/self-host/deploy/advanced-deployments/local-source-code#start-middlewares-with-docker-compose) and is not used here.

            For example, create an OpenSearch override file if you don't already have one:

            ```bash
            cd /dify
            cp -n envs/vectorstores/opensearch.defaults envs/vectorstores/opensearch.env
            ```

        In your copy, edit the input values and leave the **Container variable mappings** expressions unchanged.

        For these OpenSearch settings, `/dify/.env` takes precedence over `opensearch.env`. Follow each template's comments for other services; some load only their service file or specific root inputs.

        If your AWS deployment injects variables through `docker-compose.override.yaml`, keep those settings there. Service-level `environment:` values in Compose take precedence over env-file values.
    </Step>
    <Step title="Apply Changes">
        From `/dify`, validate the configuration and recreate the affected services. Keep your existing AWS override file in both commands; if it is absent, omit `-f docker-compose.override.yaml`.

        ```bash
        cd /dify
        docker compose -f docker-compose.yaml -f docker-compose.override.yaml config --quiet
        docker compose -f docker-compose.yaml -f docker-compose.override.yaml up -d
        ```

    </Step>
</Steps>

### Web App Logo & Branding

In **Settings** > **Customization**, you can remove the `Powered by Dify` branding or replace it with your own logo.

## Upgrade

<Warning>

    - Choose a release from the [Release Notes](https://github.com/langgenius/dify/releases) and read its upgrade instructions before updating.

    - The current Docker files require Docker Compose 2.35.0 or later. Run `docker compose version` to confirm before upgrading.

</Warning>

Run the commands on your EC2 instance with the same Compose project name and files as your existing deployment. If you use `-p` or `COMPOSE_PROJECT_NAME`, keep its value so named volumes remain attached. If `docker-compose.override.yaml` is absent, omit its `-f` option below.

<Steps>
    <Step title="Back Up the Deployment">
        Back up `/dify/.env`, every local `.env` file under `/dify/envs/`, `docker-compose.override.yaml`, and other custom deployment files. Preserve your working secrets, including the explicit or stored [SECRET_KEY](/en/self-host/deploy/configuration/environments#secret_key), and volume paths.

        Back up persistent data with your deployment's backup process. Include `/dify/volumes/` and any external databases or storage.

        If `local_sandbox` is configured, also back up its named volumes mounted at `/home/dify` and `/workspace`. From `/dify`, identify their actual Docker names, keeping your existing project and file options. This works for running or stopped containers:

        ```bash
        docker inspect --format '{{range .Mounts}}{{if eq .Type "volume"}}{{println .Name .Destination}}{{end}}{{end}}' "$(docker compose -f docker-compose.yaml -f docker-compose.override.yaml ps --all --quiet local_sandbox)"
        ```

        Back up the volumes returned by this command.

        Use consistent database backups; copying database files while they are being written is not a reliable backup.
    </Step>
    <Step title="Update to the Selected Release">
        Replace `<version>` with the release tag you chose. Copy its Docker files and templates together:

        ```bash
        release_tag="<version>"
        upgrade_dir="$(mktemp -d)"
        git clone --depth 1 --branch "$release_tag" https://github.com/langgenius/dify.git "$upgrade_dir/dify"
        rsync -av --exclude='.env' --exclude='*.env' \
          --exclude='docker-compose.override.yaml' --exclude='volumes/' \
          "$upgrade_dir/dify/docker/" /dify/
        ```

        The exclusions preserve your local environment files, AWS override file, and runtime data. Reapply changes to any other custom deployment files from your backup.
    </Step>
    <Step title="Review Your Configuration">
        Compare `/dify/.env.example` with your existing `/dify/.env` for required startup inputs. Compare each local service `.env` file with its matching `.defaults` or `.env.example` template.

        Existing `shared.env` files remain supported. Compare both `api-worker.env` and an existing `shared.env` with `envs/core-services/api-worker.defaults`.

        Add the settings you need to your existing files; copying a template over them discards your overrides. If the local sandbox token is missing, generate one with `openssl rand -hex 32`. In `/dify/.env`, set [`DIFY_AGENT_LOCAL_SANDBOX_AUTH_TOKEN`](/en/self-host/deploy/configuration/environments#dify_agent_local_sandbox_auth_token) to the output.

        Keep your existing database and vector store selectors and volume paths. Changing a selector does not migrate data. For a new optional override, follow [Configuration](#configuration) to create its local file.
    </Step>
    <Step title="Apply and Check the Upgrade">

        ```bash
        cd /dify
        docker compose -f docker-compose.yaml -f docker-compose.override.yaml config --quiet
        docker compose -f docker-compose.yaml -f docker-compose.override.yaml pull
        docker compose -f docker-compose.yaml -f docker-compose.override.yaml up -d
        docker compose -f docker-compose.yaml -f docker-compose.override.yaml ps --all
        ```

        Check that long-running services are `Up` or `healthy` and that `init_permissions` finishes with `Exited (0)`. Open Dify and check the features that use your custom settings.
    </Step>
</Steps>
