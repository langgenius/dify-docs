---
title: Dify Premium on AWS
description: Deploy, customize, and upgrade Dify Premium on AWS
---

Dify Premium is our AWS AMI offering that allows custom branding and is one-click deployable to your AWS VPC as an EC2 instance. Head to [AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-t22mebxzwjhu6) to subscribe. It's useful in a couple of scenarios:

- You're looking to create one or a few applications as a small/medium business and you care about data residency.
- You are interested in [Dify Cloud](https://cloud.dify.ai), but your use case requires more resources than supported by the [plans](https://dify.ai/pricing).
- You'd like to run a POC before adopting Dify Enterprise within your organization.

## Access & Set up

After the AMI is deployed, access Dify via the instance's public IP found in the EC2 console (HTTP port 80 is used by default).

If this is your first time accessing Dify, enter the Admin initialization password (your EC2's instance ID) to start the setup process.

## Customize

### Configuration

Use Docker Compose 2.35.0 or later. Run `docker compose version` to check.

<Steps>
    <Step title="Edit Environment Variables">
        Put each setting where [Set a Variable](/en/self-host/deploy/configuration/environments#set-a-variable) says it goes:

        - Settings Compose reads first, such as `COMPOSE_PROFILES` and `VECTOR_STORE`, and the shared credentials go in `/dify/.env`.
        - Settings your AWS deployment already sets in `docker-compose.override.yaml` stay there.
        - Every other setting goes in a local `.env` file under `/dify/envs/`, never in a `.defaults` file.

        For example, to change an OpenSearch setting, copy its defaults file once, then edit the copy:

        ```bash
        cd /dify
        cp -n envs/vectorstores/opensearch.defaults envs/vectorstores/opensearch.env
        ```

    </Step>
    <Step title="Apply Changes">
        From `/dify`, validate the configuration and recreate the affected services. Keep your existing AWS override file in both commands; if it is absent, omit `-f docker-compose.override.yaml`.

        ```bash
        cd /dify
        docker compose -f docker-compose.yaml -f docker-compose.override.yaml config --quiet
        docker compose -f docker-compose.yaml -f docker-compose.override.yaml up -d
        ```

        If a change doesn't take effect, check whether `/dify/.env` or `docker-compose.override.yaml` also sets it: both win over a local file (see [Precedence](/en/self-host/deploy/configuration/environments#precedence)).
    </Step>
</Steps>

### Web App Logo & Branding

In **Settings** > **Customization**, you can remove the `Powered by Dify` branding or replace it with your own logo.

## Upgrade

<Warning>
    Choose a release from the [Release Notes](https://github.com/langgenius/dify/releases) and read its upgrade guide before updating.
</Warning>

Run every Compose command below on your EC2 instance with the deployment's existing project name and files, including any `-p` or `COMPOSE_PROJECT_NAME`. A different project name starts with new, empty named volumes. If you don't have `docker-compose.override.yaml`, leave out its `-f` option.

<Steps>
    <Step title="Back Up the Deployment">
        1. From `/dify`, stop the deployment so the databases aren't writing while you copy their files:

            ```bash
            docker compose -f docker-compose.yaml -f docker-compose.override.yaml stop
            ```

            If you can't stop it, back up the databases with their own dump tools instead.

        2. Back up `/dify/.env`, every local `.env` file under `/dify/envs/`, `docker-compose.override.yaml`, and other custom deployment files. Then back up persistent data, including `/dify/volumes/` and any external databases or storage.

        3. If your deployment includes `local_sandbox`, also back up its named volumes, mounted at `/home/dify` and `/workspace`. List them with:

            ```bash
            docker inspect --format '{{range .Mounts}}{{if eq .Type "volume"}}{{println .Name .Destination}}{{end}}{{end}}' "$(docker compose -f docker-compose.yaml -f docker-compose.override.yaml ps --all --quiet local_sandbox)"
            ```

    </Step>
    <Step title="Update to the Selected Release">
        Replace `<version>` with the release tag you chose. Copy its Docker files and templates together:

        ```bash
        release_tag="<version>"
        upgrade_dir="$(mktemp -d)"
        git clone --depth 1 --branch "$release_tag" https://github.com/langgenius/dify.git "$upgrade_dir/dify"
        rsync -av --exclude='.env' --exclude='*.env' \
          --exclude='docker-compose.override.yaml' --exclude='volumes/' \
          "$upgrade_dir/dify/docker/" /dify/
        ```

        The exclusions preserve your local environment files, AWS override file, and runtime data. Reapply changes to any other custom deployment files from your backup.
    </Step>
    <Step title="Review Your Configuration">
        Compare `/dify/.env` with `/dify/.env.example`, and each local file under `/dify/envs/` with its new template. Where they differ:

        - Keep the values you set on purpose, including your database and vector store settings.
        - Take the template's value for the rest.
        - Use the new name where the release notes rename a setting.

        Don't copy a template over your file: that discards your overrides.

        <Note>
            If `/dify/.env` doesn't set [`DIFY_AGENT_LOCAL_SANDBOX_AUTH_TOKEN`](/en/self-host/deploy/configuration/environments#dify_agent_local_sandbox_auth_token) yet, generate a value with `openssl rand -hex 32` and set it there. The agent backend and its local sandbox require this shared token to start.
        </Note>
    </Step>
    <Step title="Apply and Check the Upgrade">

        ```bash
        cd /dify
        docker compose -f docker-compose.yaml -f docker-compose.override.yaml config --quiet
        docker compose -f docker-compose.yaml -f docker-compose.override.yaml pull
        docker compose -f docker-compose.yaml -f docker-compose.override.yaml up -d
        docker compose -f docker-compose.yaml -f docker-compose.override.yaml ps --all
        ```

        Check that long-running services are `Up` or `healthy` and that `init_permissions` finishes with `Exited (0)`. Then open Dify and check the features that use your custom settings.
    </Step>
</Steps>
