## Find Your Apps

Run `difyctl get console_app` to list your apps. Only apps with Service API access turned on are listed, and only those can be run.

```bash
difyctl get console_app

# narrow by part of the name, by mode, or both
difyctl get console_app --name report --mode workflow
```

Use an app's `id` as `--app-id` in other commands. Its `mode` is the app's type, which decides the command that runs it:

| `mode` | App type | Run it with |
|:---|:---|:---|
| `workflow` | Workflow | `run console_app workflow` |
| `advanced-chat` | Chatflow | `run console_app advanced_chat` |
| `chat` | Chatbot | `run console_app chat` |
| `agent-chat` | Legacy Agent | `run console_app chat` |
| `completion` | Text Generator | `run console_app completion` |

<Info>
`difyctl` doesn't list or run apps built with the new Agent. Call them through the [Service API](/en/api-reference/guides/agent) instead.
</Info>

## Check an App's Inputs

Run `difyctl describe console_app` to show an app's variables: their names, their types, and which are required.

```bash
difyctl describe console_app --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b
```

## Run a Workflow

Pass the app's variables to `difyctl run console_app workflow` in `--inputs`, as JSON keyed by name. The answer is the result's `outputs`, keyed by the Output node's variables.

```bash
difyctl run console_app workflow --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --inputs '{"topic": "quarterly report"}'

# read the variables from a file
difyctl run console_app workflow --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --inputs @inputs.json
```

<Note>
A misspelled required variable fails the run with an error such as `topic is required in input form`. A misspelled optional one is silently left out. Check the variable names with [`describe console_app`](#check-an-apps-inputs).
</Note>

## Send a Message or Generate Text

Use the `run console_app` command that matches the app's type in [Find Your Apps](#find-your-apps). Put the message in `--query` and any variables in `--inputs`. A Text Generator app usually takes only `--inputs`. The response is the result's `text.answer`.

```bash
# a Chatbot or legacy Agent app
difyctl run console_app chat --app-id 0a1b2c3d-4e5f-6789-abcd-ef0123456789 --query "What are your business hours?"

# a Chatflow app with one variable
difyctl run console_app advanced_chat --app-id 3c4d5e6f-7a8b-4c9d-8e0f-1a2b3c4d5e6f --query "What changed this quarter?" --inputs '{"topic": "quarterly report"}'

# a Text Generator app
difyctl run console_app completion --app-id 5e6f7a8b-9c0d-4e1f-a2b3-c4d5e6f7a8b9 --inputs '{"topic": "quarterly report"}'
```

## Continue a Conversation

Pass the result's `conversation_id` back with `--conversation-id`.

```bash
difyctl run console_app advanced_chat --app-id 3c4d5e6f-7a8b-4c9d-8e0f-1a2b3c4d5e6f --query "What changed this quarter?" --inputs '{"topic": "quarterly report"}'

# reply in the same conversation, with the same variables
difyctl run console_app advanced_chat --app-id 3c4d5e6f-7a8b-4c9d-8e0f-1a2b3c4d5e6f --conversation-id 9f8e7d6c-5b4a-4321-8fed-cba987654321 --query "And the quarter before?" --inputs '{"topic": "quarterly report"}'
```

<Note>
Send the app's required variables again on every turn. A message without them fails.
</Note>

## Send Files

With any run command, map each file variable to a local path in `--files`. A file-list variable takes a list of paths. A file on the web goes in `--inputs` instead. Pass each file variable in either `--files` or `--inputs`, not both.

```bash
difyctl run console_app workflow --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --inputs '{"topic": "quarterly report"}' --files '{"document": "./report.pdf", "appendices": ["./q1.pdf", "./q2.pdf"]}'

# a file on the web
difyctl run console_app workflow --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --inputs '{"document": {"transfer_method": "remote_url", "url": "https://example.com/report.pdf", "type": "document"}}'
```

## Follow a Long Run

To watch a run as it goes, add `--stream`. It prints each event as it happens, one JSON object per line. In a Workflow run, the last event, `workflow_finished`, carries the result in `data.outputs`. To print only the events you want, name each one with `--only`.

```bash
difyctl run console_app workflow --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --inputs '{"topic": "quarterly report"}' --stream

# print only the last event
difyctl run console_app workflow --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --inputs '{"topic": "quarterly report"}' --stream --only workflow_finished
```

## Stop a Run

To stop a Workflow or Chatflow run that's still going or paused at a Human Input form, pass its run ID to `difyctl stop run`. For a Chatbot, legacy Agent, or Text Generator reply, use [`stop task`](#stop-a-chatbot-legacy-agent-or-text-generator-reply) instead.

```bash
difyctl stop run --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --run-id 4b5c6d7e-8f90-4a1b-b2c3-d4e5f6a7b8c9
```

Take the run ID from wherever you have it:

- A `suspended` or `incomplete` result, in `run_id`.
- A `--stream` run's events, in `workflow_run_id`. In a Chatflow, `message` and `message_end` events don't carry it: take it from `workflow_started` or a node event.
- The app's list of running runs, when you have no run ID, such as for a run started from the web app, or an `incomplete` result without a `run_id`:

  ```bash
  difyctl get run --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --triggered-from app-run --status running
  ```

  For a run paused at a form, leave out `--status` and look for runs whose `status` is `paused`: `--status` can't select them. To find a test run of the draft instead, leave out `--triggered-from app-run`.

<Info>
Pressing Ctrl+C during a Workflow or Chatflow run stops only `difyctl`, not the run on the server. To stop the run too, pass its run ID to `stop run`.
</Info>

A run that's still going stops right away. A model call or HTTP request already under way still completes, and its cost and side effects remain. When you stop a run paused at a form, its forms stop accepting answers.

To confirm the run stopped, pass its run ID to `difyctl describe run` and check that its `status` is `stopped`. It can still show `running` for a while after the stop, so check again after a moment. Running `stop run` again is safe: on a run you've already stopped, it succeeds too.

If the command that started the run is still following it when the stop lands, the command exits 1, as for a [failed run](/en/cli/reference/results-errors-and-exit-codes#check-how-a-run-ended). With `--stream`, its last event shows the stop: `workflow_finished`, with `data.status` set to `stopped`. Without `--stream`, its result's `status` is `failed`. To tell a stop from a failure in a script, check the run's `status` with `describe run`.

A stopped Chatflow run's result has no `conversation_id`, so you can't continue the conversation from it.

When a stop fails, the error in your terminal starts with one of these codes. To branch on them in a script, see [Read an Error](/en/cli/reference/results-errors-and-exit-codes#read-an-error).

- `run_not_found`: the app has no run with that ID. Check that you passed the run ID, not a `task_id`, and that `--app-id` is the app the run belongs to.
- `run_not_stoppable`: the run already succeeded, failed, or partially succeeded, or the server stopped it for exceeding a time or step limit.

  A run paused at a form can get this code too. If you started it yourself, such as with `difyctl` or as a test run, run `get run event` once with its run ID and `--include-state-snapshot`, then run `stop run` again. Any other such run, including one started from a shared web app or through the Service API, can't be stopped from `difyctl`.
- `app_mode_mismatch`: the command doesn't match the app's type. Use `stop run` for a Workflow or Chatflow app, and `stop task` for the other types.

### Stop a Chatbot, Legacy Agent, or Text Generator Reply

To be able to stop a reply, start it with `--stream`. Then pass the `task_id` from its first event to `difyctl stop task`.

```bash
difyctl stop task --app-id 0a1b2c3d-4e5f-6789-abcd-ef0123456789 --task-id 26992456-d005-4add-a26d-8dff91d5f13d
```

<Note>
`stop task` prints `{"result": "success"}` even for a task ID that doesn't exist, or a reply that has already finished. So check that the `task_id` is from the reply you want to stop, and run `stop task` while its stream is still open.

Nothing in the reply marks the stop, either. Its stream ends with `message_end`, and the command that started it exits with code 0, as for a finished reply. The answer holds only what arrived before the stop. If your script uses the answer, have it record that it called `stop task`.
</Note>

## Answer a Human Input Form

<Info>
You can answer a form from `difyctl` only when the Human Input node delivers it through **Webapp**.
</Info>

A run that pauses at the form returns a result whose `status` is `suspended`, with one hint per action button. [Run the hint](/en/cli/find-and-run-commands#follow-hints) for your action, replacing each `null` in its `inputs` with your answer.

Or, to see the form's fields before you answer, take `form_token` from any hint and use `describe run form`, then answer with `submit run form`.

Either way, follow the resumed run with `get run event`, passing the paused result's `run_id` as `--run-id`. Keep `--include-state-snapshot`, or the command can sit silent for up to 5 minutes.

```bash
# show the form's fields
difyctl describe run form --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --form-token Xq7Lm2RtPz9KcV4bN8wJdE

# submit with an action; use --inputs '{}' when the form has no fields
difyctl submit run form --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --form-token Xq7Lm2RtPz9KcV4bN8wJdE --action approve --inputs '{"comment": "Looks good"}'

# follow the resumed run
difyctl get run event --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --run-id 4b5c6d7e-8f90-4a1b-b2c3-d4e5f6a7b8c9 --include-state-snapshot

# keep following if the run can pause at another form later
difyctl get run event --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --run-id 4b5c6d7e-8f90-4a1b-b2c3-d4e5f6a7b8c9 --include-state-snapshot --continue-on-pause
```

## Find Why a Run Failed

For a Workflow or Chatflow run, start from the failed result's `run_id`, or list failed runs with `difyctl get run`. Then inspect the run with `describe run` and its nodes with `get run node`.

```bash
difyctl get run --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --triggered-from app-run --status failed

# the run's inputs, outputs, status, and error
difyctl describe run --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --run-id 4b5c6d7e-8f90-4a1b-b2c3-d4e5f6a7b8c9

# each node; the failed one carries the error
difyctl get run node --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --run-id 4b5c6d7e-8f90-4a1b-b2c3-d4e5f6a7b8c9
```

<Note>
Keep `--triggered-from app-run`. Without it, the list shows only test runs of the draft.
</Note>

## Troubleshooting

| Message | What to do |
|:--|:--|
| `invalid run input`, though the inputs are right | The app may never have been published. Publish it, then run it again. |
| `unknown flag "--task-id"` from `stop run` or `get run event` | Pass the run ID as `--run-id` instead, such as a result's `run_id`. To stop a Chatbot, legacy Agent, or Text Generator reply by its `task_id`, use [`stop task`](#stop-a-chatbot-legacy-agent-or-text-generator-reply). |

For errors that can come from any command, see [Troubleshooting](/en/cli/reference/results-errors-and-exit-codes#troubleshooting) on Results, Errors, and Exit Codes.
