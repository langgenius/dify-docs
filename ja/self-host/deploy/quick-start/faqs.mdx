## デプロイ方法

### 旧バージョンのインストール

`--branch` フラグを使用して特定のバージョンをインストールします：

```bash
git clone https://github.com/langgenius/dify.git --branch 0.15.3
```

残りのセットアップは最新版のインストールと同じです。

### ZIP アーカイブを使用したインストール

ネットワーク制限がある環境や git が利用できない場合：

```bash
# 最新リリースをダウンロード
wget -O dify.zip "$(curl -s https://api.github.com/repos/langgenius/dify/releases/latest | jq -r '.zipball_url')"
unzip dify.zip && rm dify.zip
```

または、別のデバイスで ZIP をダウンロードして手動で転送することもできます。

**アップグレードするには**：

```bash
wget -O dify-latest.zip "$(curl -s https://api.github.com/repos/langgenius/dify/releases/latest | jq -r '.zipball_url')"
unzip dify-latest.zip && rm dify-latest.zip
rsync -a dify-latest/ dify/
rm -rf dify-latest/
cd dify/docker
docker compose pull
docker compose up -d
```

### クローン時の「Remote branch null not found」エラー

[Docker Compose で Dify をデプロイする](/ja/self-host/deploy/quick-start/docker-compose) のクローンコマンドは、GitHub API を通じて Dify の最新バージョンを取得します。このリクエストが失敗すると（未認証リクエストに対する GitHub のレート制限が主な原因）、`jq` が `null` を出力し、git は `fatal: Remote branch null not found in upstream origin` を報告します。

代わりに、バージョンを明示してクローンしてください。[Dify releases](https://github.com/langgenius/dify/releases) で最新バージョンを確認し、次のコマンドを実行します：

```bash
git clone --branch <version> https://github.com/langgenius/dify.git
```

`--branch` なしでもクローンできます。`main` ブランチの Compose ファイルは最新リリース版のイメージを指定しているため、起動されるのはリリース版です。ただし、Compose ファイルや環境変数テンプレートなどのデプロイ用ファイル自体は開発中の内容であり、リリース版と異なる場合があります。

## バックアップ手順

### アップグレード前のバックアップ作成

データ損失を防ぐため、アップグレード前は必ずバックアップを行ってください：

```bash
cp -r dify "dify.bak.$(date +%Y%m%d%H%M%S)"
```

これにより、復元しやすいタイムスタンプ付きのバックアップが作成されます。

## リバースプロキシ設定

### フロントエンドとバックエンドが異なるサブドメインで動作する場合のログインセッション切れ

Web と API を異なるサブドメインに分けてリバースプロキシ経由で公開している場合、認証 Cookie が両方のホストに届きません。たとえば UI が `app.example.com`、バックエンドが `api.example.com` の構成です。ログインは成功したように見えても、次のリクエストでセッションが切れます。

`.env` で両方の変数を設定し、Dify を再起動してください：

- **`COOKIE_DOMAIN`**：共有するトップレベルドメインを指定します（例：`example.com`）。先頭のドットは省略可能です。
- **`NEXT_PUBLIC_COOKIE_DOMAIN`**：`1` を設定すると、フロントエンドでサブドメイン間の Cookie 共有が有効になります。

```bash
docker compose down
docker compose up -d
```

Cookie はトップレベルドメインを越えて共有できないため、フロントエンドとバックエンドは同じ登録可能ドメイン内にある必要があります。詳細は [環境変数](/ja/self-host/deploy/configuration/environments) を参照してください。

### Cloudflare などのプロキシ背後で全ユーザーのサインインメールがブロックされる問題 {#sign-in-emails-blocked-behind-proxy}

全ユーザーが一斉に、サインインコードやパスワードリセットのメールを受け取れなくなります。表示されるメッセージは「Too many emails have been sent from this IP address recently. Please try again later.」です。1.18.0 以降、同梱の Nginx の前段に Cloudflare やロードバランサーなどのプロキシを置いているデプロイでは、この問題が起こり得ます。

Dify は、各ユーザーの IP アドレスを同梱の Nginx から受け取ります。プロキシの背後では、Nginx にはプロキシのアドレスしか見えません。そのため、プロキシのアドレスに対する制限を全ユーザーで共有することになります。

構成によっては、プロキシが同梱の Nginx を経由せず、`api` と `web` のコンテナへ直接転送します。Cloudflare Tunnel や Nginx Proxy Manager の一部の構成がこれに当たります。この場合は以下の手順を飛ばし、代わりに次の点を確認してください：

- プロキシが `X-Forwarded-For` を設定していること。設定していないと、すべてのユーザーがプロキシのアドレスからのアクセスとして扱われます。
- API にはプロキシ経由でしかアクセスできないこと。API に直接アクセスできる人は、Dify が認識するアドレスを自由に指定できてしまいます。

プロキシが同梱の Nginx に転送している場合は、信頼するプロキシを Nginx に設定します：

<Steps>
  <Step title="プロキシのアドレスを確認">
    Nginx のアクセスログ（`docker compose logs nginx`）では、各行の先頭にプロキシの接続元アドレスが記録されています。プロキシが同じサーバー上にある場合も、`127.0.0.1` と仮定せず、ログで確認してください。

    Cloudflare が Nginx に直接接続している場合、この手順は飛ばしてください。
  </Step>
  <Step title="real-ip.conf を作成">
    構成に合わせて `docker/nginx/conf.d/real-ip.conf` を作成します。Nginx はこのディレクトリ内の `.conf` ファイルをすべて読み込むよう設定済みです。作成したファイルは、アップグレード後もそのまま残ります。

    <Tabs>
      <Tab title="ロードバランサーまたはリバースプロキシ">
        `X-Forwarded-For` を設定するプロキシの場合：

        ```nginx
        # プロキシの接続元アドレスまたは CIDR 範囲に置き換えてください。
        set_real_ip_from 192.0.2.10/32;
        real_ip_header X-Forwarded-For;
        real_ip_recursive on;
        ```

      </Tab>
      <Tab title="Cloudflare">
        Cloudflare が Nginx に直接接続している場合は、[Cloudflare の IP 範囲](https://www.cloudflare.com/ips/) をすべて信頼します：

        ```nginx
        # Cloudflare が公開している IPv4 と IPv6 の範囲ごとに 1 行ずつ記述します。
        set_real_ip_from <cloudflare-range>;
        # ...
        real_ip_header CF-Connecting-IP;
        ```

        これらの範囲は Cloudflare のネットワーク全体を表すもので、自分のゾーン専用ではありません。そのため、Authenticated Origin Pulls などを使って [オリジンサーバーへのアクセス元も制限](https://developers.cloudflare.com/fundamentals/security/protect-your-origin-server/) してください。
      </Tab>
      <Tab title="複数のプロキシ">
        Cloudflare を通ったあと、さらに自分のサーバー上のプロキシを経由するような多段構成では、経路上のプロキシをすべて信頼します。対象は、自分のサーバー上のプロキシと [Cloudflare の IP 範囲](https://www.cloudflare.com/ips/) のすべてです。Nginx の直前のプロキシだけを信頼すると、Dify にはユーザーのアドレスではなく Cloudflare のアドレスが見えてしまいます。

        ```nginx
        # 自サーバーで動くプロキシの接続元アドレスに置き換えてください。
        set_real_ip_from 192.0.2.10/32;
        # Cloudflare が公開している IPv4 と IPv6 の範囲ごとに 1 行ずつ記述します。
        set_real_ip_from <cloudflare-range>;
        # ...
        real_ip_header X-Forwarded-For;
        real_ip_recursive on;
        ```

        経路上の各プロキシが、`X-Forwarded-For` に追記する設定になっている必要があります。
      </Tab>
    </Tabs>

    <Warning>
      `0.0.0.0/0`、`::/0`、および信頼できないマシンも接続しているネットワークは、決して信頼しないでください。信頼すると、Nginx にアクセスできる人なら誰でも、Dify が認識する IP アドレスを自由に指定できてしまいます。
    </Warning>
  </Step>
  <Step title="Nginx をリロード">

    ```bash
    docker compose exec nginx nginx -s reload
    ```

    これで、`docker compose logs nginx` に出力される新しい行の先頭が、プロキシではなく各ユーザー自身のアドレスになるはずです。ユーザーはブロックされたアドレスを共有しなくなるため、すぐにメールを再リクエストできます。
  </Step>
</Steps>
