## カスタム評価器の仕組み

カスタム評価器は、評価ワークフローとして公開した Workflow アプリです。評価では、テストセットの行ごとに 1 回ずつ実行されます。

評価器のユーザー入力ノードは、評価対象のワークフローをその行で実行した結果から、選んだ値を受け取ります。受け取れるのは、入力変数（質問など）やノードの出力（回答など）です。評価器はテストセットの参照回答を読み取れないため、参照回答との比較は組み込み指標に任せてください。

評価器の出力ノードの各変数は、その行のカスタム指標として返されます。

1 つの評価で使えるカスタム評価器は 1 つだけです。複数のルールをチェックするには、すべてを 1 つの評価器にまとめ、個別に判定したいルールごとに出力を分けます。

評価器の実行は、そのアプリの通常の実行として扱われます。評価器の **ログ** には、処理した行ごとに 1 件ずつ記録されます。[AI クレジット](/ja/cloud/use-dify/workspace/model-providers#ai-クレジットでのモデル利用) を使うモデルでは、評価器のモデル呼び出しもクレジットから差し引かれます。

## 評価器の構築

たとえば、サポート用の Workflow アプリが `question` を受け取り、ナレッジベースから関連する文章を検索して、その内容をもとに LLM ノードが回答するとします。チームでは、すべての回答に次のスタイルを求めています。質問の内容に答えること、約 250 文字以内に収めること、ユーザーが取れる次のステップで締めくくることです。

これらのルールをチェックする Workflow アプリを作成し、`Support Style Check` という名前を付けます。評価ワークフローにはトリガーノードと人間の入力ノードを含められないため、これらは追加しないでください。

### チェックする値の受け取り

ユーザー入力ノードで、評価器が受け取る値ごとに入力変数を追加します。回答が質問に答えているかを判断するには、質問と回答の両方が必要です。そこで、段落タイプの変数を 2 つ（`question` と `answer`）追加します。

### ルールに基づく採点

採点に使うノードは、ルールに応じて選びます。

- 回答が質問に答えているかなど、判断を伴うルールには、採点基準を設定した LLM ノードが必要です。
- 文字数や必須の値など、スクリプトで厳密にチェックできるルールには、コード実行ノードが適しています。

この例では長さの上限はおおよその目安なので、3 つのルールすべてを 1 つの LLM ノードで判定できます。

`Style Check` という名前の LLM ノードを追加し、温度を 0 に設定します。採点するノードは、同じ回答に毎回同じスコアを付ける必要があるためです。システムインストラクションには、ルールと、結果ごとに付けるスコアを書きます。

```text wrap
あなたの役割は、サポートの回答を次の 3 つのスタイルルールに照らしてレビューすることです。
1. 質問の内容に答えていること。
2. 約 250 文字以内であること。
3. ユーザーが取れる次のステップで締めくくっていること。

0 から 1 のスコアを付けてください。3 つのルールをすべて満たす場合は 1、2 つ満たす場合は 0.67、1 つ満たす場合は 0.33、1 つも満たさない場合は 0 です。
あわせて、回答が守っていないルールを挙げた 1 行の理由を書いてください。
```

結果ごとのスコアを明示しておけば、同じルールに違反した 2 つの回答には同じスコアが付きます。また、1 行の理由を見れば、回答がどのルールに違反したかを結果の画面で確認できます。

ユーザーメッセージには、2 つの入力変数を挿入します。

```text
質問：{{question}}
回答：{{answer}}
```

### 判定条件で使えるスコアの出力

各出力は 1 つの指標になり、その型によって、判定条件でどのように判定できるかが決まります。

- **Number**（整数または小数。`score` など）：≥ 0.8 のように、しきい値と比較します。
- **Boolean**（`passed` フラグなど）：true か false かを判定します。
- **String**（`reason` など）とその他の型：Contains などの演算子で、テキストとして比較します。

しきい値を設定するスコアは、数値でなければなりません。`Style Check` に戻って [構造化出力](/ja/cloud/use-dify/nodes/llm#構造化出力) をオンにし、必須フィールドを 2 つ追加します。

| フィールド | 型 | 説明 |
|:------|:-----|:------------|
| `score` | number | 0 から 1 のスコア |
| `reason` | string | 1 行の理由 |

続いて、両方のフィールドを [出力](/ja/cloud/use-dify/nodes/output) ノードに追加します。

- `score`：`Style Check` の `structured_output.score` を指定
- `reason`：`Style Check` の `structured_output.reason` を指定

## 評価ワークフローとしての公開

エディターで、サンプルの質問と回答を使って評価器を一度実行します。返された `score` と `reason` が妥当であれば、**公開する** メニューを開き、**評価ワークフローとして公開** をクリックします。

公開済みの Workflow アプリを評価器にする場合は、代わりに **評価ワークフローに切り替える** を選びます。変換されるのは現在公開中のバージョンなので、ドラフトに変更がある場合は先に公開してください。

評価ワークフローは標準ワークフローに戻せます。ただし、その評価器を使う評価は、評価ワークフローに戻すまで実行できません。

## 評価への追加

サポート用の Workflow アプリの **Evaluation** ページを開きます。**Add Metric** > **Custom metrics** をクリックし、`Support Style Check` を選択します。

**Variable Mapping** で、評価器の各入力変数が、サポート用の Workflow アプリの公開済みバージョンから何を受け取るかを選びます。

- `question`：ユーザー入力ノードの `question`
- `answer`：LLM ノードの `text`（回答そのもの）

評価対象のワークフローが分岐する場合は、どの経路でも実行されるノードからマッピングします。分岐ごとに別のノードが回答を出力する場合は、[変数集約器](/ja/cloud/use-dify/nodes/variable-aggregator) ノードでそれらをまとめ、そのノードからマッピングします。

## 出力による行の合否判定

**Judgment Conditions** で、条件 `Support Style Check / score` ≥ 0.8 を追加します。スタイルルールを 1 つでも守っていない回答はスコアが 0.8 未満になるため、すべてのルールに従った回答だけが合格します。

カスタム指標と組み込み指標は、同じ判定条件の中で組み合わせられます。たとえば評価で LLM ノードの Faithfulness も採点している場合は、Faithfulness ≥ 0.8 も追加します。そのうえで、2 つの条件を AND で結合します。

## 評価器の更新と削除

- **ルールの更新**：評価器を編集して公開します。更新内容は、その後に開始した実行から適用されます。

- **削除**：削除すると、その評価器を使っている実行はキャンセルされます。先に、実行中のものがないことを確認してください。削除した評価器は、それを使うすべての評価から、出力に対する条件ごと取り除かれます。ほかに指標がなかった評価では、保存済みの設定がすべて失われます。

## 評価器が行の採点に失敗する場合

行に `EVAL_CUSTOM_EVALUATOR_FAILED` が表示される主な原因は次のとおりです。

- **マッピングした値がその行にない**：値の取得元のノードが実行されなかった場合や、実行されてもマッピングしたフィールドを出力しなかった場合です。分岐によってそのノードがスキップされた場合は、代わりにどの経路でも実行されるノードからマッピングしてください。

- **マッピングした値が評価器の入力変数に合わない**：テキストではない値や、変数の長さの上限を超えるテキストなどです。この場合は評価器が実行されないため、評価器のログには何も表示されません。各マッピングが、変数の型と長さの上限に合っているかを確認してください。

- **評価器の実行が失敗した**：モデルの呼び出しでエラーが発生した場合などです。評価器アプリの [ログ](/ja/cloud/use-dify/monitor/logs) でその実行を探し、何が起きたかを確認してください。

- **評価器の作成者がワークスペースを離れた**：評価器は作成者のアカウントで実行されるため、すべての行が失敗します。現在のメンバーに代わりの評価器を作成してもらい、評価ワークフローとして公開したうえで、古い評価器の代わりに評価に設定してください。
