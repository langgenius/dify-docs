> このドキュメントは AI によって自動翻訳されています。不正確な部分がある場合は、[英語版](/en/cloud/use-dify/monitor/integrations/integrate-opentelemetry) を参照してください。

OpenTelemetry は、ソフトウェアの実行中の動作を記録するためのオープン標準で、ほとんどの監視バックエンドが対応しています。実行ごとに 1 つのトレースが作られ、トレースはステップごとに 1 つのスパンで構成されます。

OpenTelemetry を選ぶと、アプリや Agent の実行が完了するたびに、チームですでに使っているバックエンドにトレースを送信できます。送信したトレースは、他のサービスのトレースと並んで表示されます。

トレース設定はアプリと Agent ごとに独立しており、送信先として使えるトレースプロバイダーは一度に 1 つだけです。複数のバックエンドに送るには、それぞれにエクスポートする OpenTelemetry Collector を Dify の送信先に指定します。

## 事前準備

<Warning>
トレースには、プロンプトを含む各実行の入力と出力が含まれます。Dify は、シークレットと思われる値もマスクしません。こうしたデータを保存してよい送信先にだけ送信してください。

Agent の実行と、[新しい Agent ノード](#agent-実行のトレース) を含むワークフローの実行では、**内容を収集** をオンにするまで内容が含まれません。
</Warning>

次のものが必要です。

- **HTTP で OpenTelemetry トレースを受け付けるエンドポイント**：OpenTelemetry Collector を使えます。OpenTelemetry を直接受け付けるバックエンドでもかまいません。

  Dify は OpenTelemetry Protocol（OTLP）のトレースを、gRPC ではなく HTTP で送信します。Collector の場合は HTTP レシーバーが受信先で、通常はポート 4318 です。
- **公開アドレス**：トレースは Dify のサーバーから送信されるため、プライベートネットワーク内やお使いのコンピューター上には届きません。
- **HTTP ヘッダー形式の認証情報**：エンドポイントが必要とする場合に用意します。たとえば `Authorization` ヘッダーや、ベンダー独自の API キー用ヘッダーです。

## Dify とエンドポイントの接続

<Info>
アプリのトレースを設定するには、オーナーまたは管理者のロールが必要です。エディターの場合は、自分が作成したアプリに限り設定できます。Agent の場合は、エディター以上のロールが必要です。
</Info>

1. アプリの **監視** ページ、または Agent の **モニタリング** ページで、**アプリのパフォーマンスの追跡** をクリックします。
2. **設定** をクリックし、フォームに入力します。

   - **Endpoint**：トレースを受信する URL です。`https://otel.example.com` のようにパスのないアドレスには Dify が `/v1/traces` を付け足し、パスがあればそのまま使います。

     URL には認証情報や `?` で始まるクエリを含めないでください。認証情報は **HTTP ヘッダー（JSON）** に入力します。
   - **HTTP ヘッダー（JSON）**：`{"Authorization":"Bearer <token>"}` のような、エンドポイントが必要とするヘッダーです。`Content-Type`、`Host`、`Accept`、`Content-Encoding` などのトランスポートヘッダーは、バックエンドのセットアップガイドに記載があっても入力しないでください。

     保存したヘッダーは二度と表示されず、**Endpoint** を変更すると削除されます。控えを手元に残しておいてください。
   - **サービス名**：バックエンドでトレースをまとめる際の名前（`service.name`）です。変更しない限り `dify` になります。後でトレースを見つけやすいように、アプリと Agent ごとに別の名前を付けてください。
   - **リソース属性（JSON）**：`{"deployment.environment.name":"production"}` のような、このアプリから送るすべてのトレースに付けるラベルです。`service.name` は **サービス名** で設定してください。

3. **保存 & 有効に** をクリックします。Dify は保存前にエンドポイントをテストします。

## 保存に失敗した場合

- **The tracing configuration could not be verified**：Dify がエンドポイントに接続できませんでした。エンドポイントがテストを拒否した場合も、このメッセージが表示されます。URL のパスとポート、インターネットからエンドポイントに到達できるかどうか、バックエンドが求めるヘッダーの名前と値を確認してください。
- **The tracing configuration is invalid**：上記のルールに反するフィールドがあります。たとえば JSON の入力ミス、トランスポートヘッダー、**Endpoint** 内の `?` クエリなどです。

## トレースの到着確認

アプリ全体を 1 回実行します。編集画面から実行しても、ユーザーとして実行してもかまいません。その後、バックエンドでアプリのサービス名を検索します。単一ノードのテストでは、アプリのトレースは送信されません。

認証情報が有効かどうかは、この実行で確実に確認できます。保存時のテストでは、認証情報を確認せずに受け付けるコレクターもあるためです。

トレースがまだ見つからない場合は、数分待ってください。Dify が再試行中のトレースは、届くまでに 5 分以上かかることがあります。

それでも届かない場合は、ヘッダーの名前と値がバックエンドの要求どおりか確認してください。Collector を経由して送信している場合は、Collector がバックエンドにトレースを転送しているかも確認します。

[Agent の実行](#agent-実行のトレース) では、Dify のログ詳細にある **外部トレース** 行でも送信状況を確認できます。

## バックエンドでのトレースの読み方

トレース内のスパンの入れ子構造は、アプリの種類によって異なります。

- **Workflow アプリ**：ルートが `workflow` で、その下にノードごとに 1 つのスパンが続きます。スパン名は `<ノードの種類>_<ノードのタイトル>` の形式で、たとえば `llm_LLM` です。各ノードのスパンは直前に実行されたノードの下に入るため、分岐のないワークフローは階段状になります。

  ```text
  workflow
  └── start_ユーザー入力
      └── llm_LLM
          └── end_出力
  ```

  入れ子になっていても、各スパンの時間はそのノード自身の実行時間だけです。

- **Chatflow アプリ**：ルートが `message` で、その下に `workflow`、さらにその下に Workflow アプリと同じ形でノードのスパンが続きます。
- **チャットボット、テキストジェネレーター、レガシー Agent アプリ**：ルートが `message` です。その下に `llm` スパンと、ナレッジベースの検索やツール呼び出しなど、その他のステップごとのスパンが入ります。`llm` スパンの長さは、モデル呼び出しだけでなくメッセージ全体の時間に相当します。
- **Agent**：ルートが `message` で、その下に Agent 自身のステップが入ります。詳しくは [Agent 実行のトレース](#agent-実行のトレース) を参照してください。

ツールとして呼び出されたワークフローは、呼び出したツールノードのスパンの下に表示されます。一方、Agent が呼び出したワークフローは、そのワークフローでトレースが有効であれば、独立したトレースを送信します。

失敗したステップを探すには、ステータスがエラーのスパンで絞り込みます。エラーの内容は、各スパンのステータスメッセージで確認できます。ノードの **例外処理** 設定でエラーを処理したステップも、絞り込み結果に含まれます。そのため、該当する実行の中には最後まで完了したものもあります。

### フィルターに使える属性

次のスパン属性を使って、トレースを絞り込んだりグループ化したりできます。たとえば `gen_ai.request.model` と `gen_ai.usage.total_tokens` から、モデルごとの token 使用量をグラフにできます。

| 属性 | 対象 | 内容 |
|:--|:--|:--|
| `dify.app_id`、`dify.workflow_run_id`、`dify.message_id`、`dify.node_execution_id` | ほとんどのスパン | アプリ、ワークフロー実行、メッセージ、ノード実行の Dify ID |
| `gen_ai.session.id` | すべてのスパン | 会話（Workflow アプリでは実行） |
| `gen_ai.user.id` | すべてのスパン | エンドユーザー。API 呼び出しの場合は、呼び出し元が送信した `user` の値 |
| `dify.span.kind` | すべてのスパン | `llm`、`retriever`、`tool`、`agent`。それ以外の種類のステップは `chain` |
| `input.value`、`output.value` | すべてのスパン | ステップの入力と出力（JSON テキスト） |
| `dify.metadata` | すべてのスパン | ステップに関する Dify のその他の詳細（JSON テキスト） |
| `gen_ai.request.model`、`gen_ai.provider.name` | LLM スパン（`dify.span.kind` = `llm`） | モデルとそのプロバイダー |
| `gen_ai.usage.input_tokens`、`gen_ai.usage.output_tokens`、`gen_ai.usage.total_tokens` | LLM スパン | token 数 |
| `dify.cost.amount`、`dify.cost.currency` | LLM スパン | 呼び出しのコスト。Dify にそのモデルの価格情報がない場合は `0` |
| `retrieval.query`、`retrieval.document` | ナレッジベースの検索 | 検索クエリと、見つかったドキュメント |

属性として token 数とコストを持つのは LLM スパンだけです。そのため、これらを合計しても、質問分類器やパラメータ抽出など、モデルを呼び出す他のノードの分は含まれません。

実行全体の token 数を知るには、`workflow` スパンの `dify.metadata` に含まれる `total_tokens` を確認します。各ノードのスパンでも、同じ場所にそのノードの `total_tokens` と `total_price` が入っています。**内容を収集** がオフの [Agent の実行](#agent-実行のトレース) では、`dify.metadata` にこれらの値は含まれません。ただし、LLM スパンには引き続き token 数とコストの属性が付きます。

### 特定の実行の検索

まず、アプリに設定したサービス名でそのアプリに絞り込みます。複数のアプリが同じ名前を使っている場合は、代わりに `dify.app_id` で絞り込んでください。これは Dify でのアプリの URL（`/app/<アプリ ID>/…`）に含まれる ID で、そのアプリのほとんどのスパンに付いています。

Agent には専用のサービス名を設定する必要があります。Agent のスパンに付くアプリ ID は、Agent の URL にある ID とは異なるためです。

アプリを絞り込んだら、手元にある ID でさらに絞り込みます。ID は API が返したとおりの形式で、ハイフンも含めて指定してください。

- **API で開始した Workflow アプリの実行**：`dify.workflow_run_id` で絞り込みます。値はレスポンスの `workflow_run_id` です。
- **API でチャットボット、テキストジェネレーター、レガシー Agent アプリに送信したメッセージ**：`dify.message_id` で絞り込みます。値はレスポンスの `message_id` です。
- **チャットボット、Chatflow アプリ、レガシー Agent アプリ、Agent の会話**：`gen_ai.session.id` で絞り込みます。値は、レスポンスの `conversation_id` か、アプリのログにある **会話 ID** です。ログではこの ID が大文字で表示されるため、コピーボタンでコピーしてください。
- **その他の実行**：開始時刻で絞り込みます。

自社サービスのセッション ID など、独自の値で実行を検索したい場合は、API で実行を開始する際に `X-Trace-Session-Id` ヘッダーでその値を送信します。すると Dify は、会話 ID や実行 ID の代わりにその値を `gen_ai.session.id` に格納します。そのため、この値を付けた会話は、会話 ID では検索できなくなります。Agent はこのヘッダーを無視します。

### 自社サービスのトレースへの合流

API で開始した Workflow アプリと Chatflow アプリの実行は、自社サービスのトレースに合流できます。これにより、自社サービスから Dify までリクエストを追跡できます。ただし、[新しい Agent ノード](#agent-実行のトレース) を含むワークフローの実行は、常に独立したトレースになります。

自社サービスの HTTP クライアントが W3C の `traceparent` ヘッダーを送信していれば、何も変更しなくても実行がトレースに合流します。OpenTelemetry の HTTP 計装は、このヘッダーを送信します。それ以外の場合は、トレース ID を `X-Trace-Id` ヘッダーで送信するか、クエリ文字列またはリクエストボディの `trace_id` として送信してください。

Dify は、ID の形式に応じて次のように扱います。

- **32 桁の 16 進数または UUID**：実行が自社サービスのトレースに合流します。OpenTelemetry のトレース ID は前者の形式です。
- **英字、数字、`-`、`_` からなる 128 文字以内の値**（`order-123` など）：実行は自社サービスのトレースに合流しません。Dify がその値からトレース ID を算出するため、同じ値で送信した実行はすべて同じトレースに入ります。
- **それ以外の値**（`order:123` など）：Dify はその値を無視し、実行は独立したトレースになります。

Dify のスパンは自社サービスと同じトレース ID を持ちます。ただしバックエンドでは、Dify を呼び出したスパンの下ではなく、トレース内の 2 つ目のルートとして表示されます。

## Agent 実行のトレース

Agent のトレースには、Agent 自身のモデル呼び出しとツール呼び出しが含まれ、`Agent attempt <n>` スパンの下にまとめられます。Agent 単体の実行では、これらのスパンはルートの `message` スパンの下に入ります。ワークフロー内では、[新しい Agent ノード](/ja/cloud/use-dify/nodes/agent#new-agent) の `agent_<ノードのタイトル>` スパンの下に入ります。

これらの実行のトレースは、他のトレースと次の点で異なります。

- **内容**：**内容を収集** をオンにするまで、入力と出力は空のまま届きます。新しい Agent ノードを含むワークフローでは、Agent だけでなくすべてのノードが対象です。
- **指定したトレース ID**：API でトレース ID を送信しても、実行ごとに独立したトレースになります。

トレース設定の **Agent データ収集** で、これらのトレースに含める内容を選択します。

- **Agent の内部処理を収集**：オフにすると、各 Agent が 1 つのステップとして表示されます。このとき、Agent のモデル名、token 数、コストも含まれなくなります。使用量を追跡している場合はオンのままにしてください。
- **内容を収集**：オンにすると、各ステップが受け取った内容と返した内容を確認できます。オンにするまでは、Dify はエラーテキストも `Application execution failed` のような汎用メッセージに置き換えます。モデル名、token 数、コストは、どちらの設定でも送信されます。

新しい Agent ノードには、Agent 自身ではなくワークフローのトレース設定が適用されます。ツールノードが呼び出したワークフローでは、**Agent の内部処理を収集** がオンでも、このノードは常に 1 つのステップとして表示されます。

## エンドポイントが停止した場合やトレースを拒否した場合

エンドポイントに接続できない場合や、エンドポイントが過負荷または障害を示す応答を返した場合、Dify は約 5 分間再試行を続けます。[Agent の実行](#agent-実行のトレース) では約 10 分間です。

障害中は、送信待ちのトレースを予備のエンドポイントに送れます。**Endpoint** を変更し、ヘッダーが同じでももう一度入力してから保存します。以降の再試行では、Dify は新しいエンドポイントに送信します。ただし、すでに始まっている Agent の実行は開始時の設定を使い続けるため、切り替わりません。

次の 2 つのよくあるケースでは、Dify は再試行せずにトレースを破棄します。

- **エンドポイントがその他の理由でトレースを拒否した場合**：たとえば、パスの誤り、認証情報の拒否、受け付けないサイズなどです。トレース設定でパスや認証情報を修正してください。トレースが大きすぎる場合は、エンドポイントのリクエストサイズ上限を引き上げます。
- **エンドポイントの応答が 30 秒以内に返らない場合**：Dify がトレースを送信した後に接続が切れた場合も同様です。バックエンドの応答が遅い場合は、その手前に OpenTelemetry Collector を置き、そちらに送信してください。Collector はトレースを受け取るとすぐに応答します。

## トレースの無効化と削除

一時的にトレースの送信を止めるには、トレース設定のスイッチをオフにします。設定は保存されたままなので、再びオンにすればそのまま使えます。

ヘッダーを含めて設定を削除するには、**削除** をクリックします。

トレースをオフにするか、アプリの送信先を別のプロバイダーに切り替えると、保留中の再試行はすべてキャンセルされます。すでに始まっている Agent の実行は、**削除** をクリックした後でも、開始時の設定で送信を最後まで行います。
