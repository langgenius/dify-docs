Dify Marketplace への提出は、[`langgenius/dify-plugins`](https://github.com/langgenius/dify-plugins) への Pull Request です。適切な提出では、1 つのパッケージだけを変更します。リポジトリのテンプレートを使い、コードから意図を推測しなくても理解できる証拠を提供してください。

<Note>
PR を開く前に [Marketplace のローカル検証](/ja/develop-plugin/publishing/marketplace-listing/prepare-plugin-for-marketplace) を実行します。CI はパッケージ検証を繰り返し、GitHub と Marketplace に固有のチェックを追加します。
</Note>

## 提出タイプの選択

<Tabs>
  <Tab title="新規プラグイン">
    作成者の名前空間にパッケージディレクトリを作成します。

    ```text
    <author>/<plugin-name>/<plugin-package>.difypkg
    ```

    メタデータ、ソースリポジトリ、連絡先、README、プライバシーポリシー、リスク開示が同じプラグインを示す必要があります。
  </Tab>
  <Tab title="バージョン更新">
    `manifest.yaml` の `version` を上げて再ビルドし、既存のプラグインディレクトリへ新しい `.difypkg` を追加します。

    更新 PR では通常、新しいパッケージファイルだけを追加します。メンテナーから指示がない限り、公開済みパッケージは残してください。**What changed** に修正、機能、移行、破壊的変更を記載します。公開パイプラインは、この内容をリリースノートに利用します。
  </Tab>
</Tabs>

## PR の作成

<Steps>
  <Step title="リポジトリの fork と同期">
    [`langgenius/dify-plugins`](https://github.com/langgenius/dify-plugins) を fork してクローンします。`main` を upstream と同期してください。

    ```bash
    git clone https://github.com/<your-github-name>/dify-plugins.git
    cd dify-plugins
    git remote add upstream https://github.com/langgenius/dify-plugins.git
    git fetch upstream
    git switch main
    git merge --ff-only upstream/main
    ```
  </Step>
  <Step title="専用ブランチの作成">
    ```bash
    git switch -c add-<plugin-name>-<version>
    mkdir -p <author>/<plugin-name>
    cp /path/to/plugin.difypkg <author>/<plugin-name>/
    ```

    変更された `.difypkg` が 1 つだけであることを確認します。

    ```bash
    git status --short
    git diff --stat
    ```
  </Step>
  <Step title="コミットとプッシュ">
    ```bash
    git add <author>/<plugin-name>/<plugin-package>.difypkg
    git commit -m "add <plugin-name> <version>"
    git push -u origin HEAD
    ```
  </Step>
  <Step title="Pull Request の作成">
    fork から `langgenius/dify-plugins:main` へ PR を作成します。パッケージと説明の両方が自動チェックと人間のレビューに対応できる場合だけ、Ready for review にしてください。
  </Step>
</Steps>

<Warning>
1 つの PR につき `.difypkg` は 1 つだけ提出してください。複数のプラグインやバージョンを含めると、CI が単一のパッケージパスを特定できず、提出がブロックされます。
</Warning>

## 提出テンプレートの記入

現在のテンプレートはレビュー契約の一部です。フィールドを削除したり、短い自由形式の説明に置き換えたりしないでください。

<AccordionGroup>
  <Accordion title="プラグイン情報">
    作成者、プラグイン名、バージョン、公開ソースリポジトリ、確認されている連絡先を記載します。`manifest.yaml` とパッケージ文書の内容に一致させてください。
  </Accordion>
  <Accordion title="提出タイプと変更内容">
    **New plugin** または **Version update** を選択し、用途や変更点を説明します。更新時は、移行や破壊的変更を含むリリースノート相当の詳細を記載してください。
  </Accordion>
  <Accordion title="リスクレベル">
    **Low risk**、**Medium risk**、**High risk** のいずれか 1 つを選択します。対応する `risk:*` ラベルが付与されます。未選択または複数選択の場合、`risk: missing` と bot コメントが追加されます。
  </Accordion>
  <Accordion title="必須チェック">
    パッケージ衛生、テスト、README の品質、プライバシー、英語ローカライズを確認してから選択します。制限がある場合は、無条件にチェックせず **Reviewer notes** で説明してください。
  </Accordion>
  <Accordion title="セキュリティとプライバシー">
    コマンドやコードの実行、SQL、SSH/SFTP、ブラウザー自動化、ファイル操作、任意 URL の取得、プロキシ、機密データ処理を記載します。すべて該当しない場合のみ `None` と記載してください。
  </Accordion>
  <Accordion title="ローカル検証とレビュアー向けメモ">
    検証コマンドと結果を貼り付けます。既知の制限、パッケージやバイナリの例外、移行事項、警告の判断に必要な背景を追加してください。
  </Accordion>
</AccordionGroup>

## レビューしやすい提出

| 推奨 | 回避 |
| :--- | :--- |
| PR のタイトル、本文、メイン README を英語で記述する。 | 主要な提出フィールドに未翻訳の CJK テキストを混在させる。 |
| パッケージに対応する正確な公開リポジトリをリンクする。 | 組織のホームページや、場所を説明しない monorepo のルートをリンクする。 |
| 機密性の高い動作が必要な理由と制約を説明する。 | オプション機能という理由で高リスク機能を低リスクと説明する。 |
| 具体的な検証コマンドと結果を記載する。 | 環境や結果なしで「テスト済み」とだけ記載する。 |
| パッケージ内容と開示を一致させる。 | バージョンが変わっても古い PR 本文を再利用する。 |

<Tip>
CI はブロッキングエラーとレビュー警告の両方を報告します。PR 本文を完全に記載すると、曖昧な警告に判断材料を与え、確認の往復を減らせます。
</Tip>

## PR 作成後

PR を作成、同期、または Ready for review にすると、プリチェックが始まります。テンプレートの選択からリスクラベルも生成されます。通常の失敗では PR を作り直さず、同じブランチへ修正をプッシュしてください。コンテキストを保ったままチェックが再実行されます。

[チェック、レビュー、Marketplace での公開](/ja/develop-plugin/publishing/marketplace-listing/marketplace-review-and-release) では、レポートの意味とマージ後の流れを説明しています。
