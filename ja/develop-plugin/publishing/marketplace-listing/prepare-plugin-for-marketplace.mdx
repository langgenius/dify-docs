## 必要なもの

- 現行の Dify Community Edition または Dify Cloud でテスト済みのプラグインプロジェクト。
- パッケージ化に使用する [Dify プラグイン CLI](https://github.com/langgenius/dify-plugin-daemon)。
- ローカル検証に使用する Python 3 と [`yq`](https://github.com/mikefarah/yq)。
- レビュアーとユーザーが確認できる公開ソースリポジトリ。

<Note>
Marketplace が受け付けるのは、ソースツリーではなく `.difypkg` パッケージです。ただし、パッケージだけでは確認できない動作を理解するため、メタデータと PR に記載されたソースリポジトリも確認されます。
</Note>

## パッケージの準備

<Tabs>
  <Tab title="実行時ファイル">
    実行時に必要なファイルだけを含めます。対象は `manifest.yaml`、プロバイダーまたはツール定義、ソースコード、依存関係、README、プライバシーポリシー、アセットです。

    `.git/`、仮想環境、キャッシュ、ログ、`.DS_Store`、ローカル設定、IDE ファイル、テスト成果物は含めないでください。`.env`、アクセストークン、秘密鍵、クラウド認証情報などのシークレットは絶対に含めないでください。
  </Tab>
  <Tab title="メタデータと文書">
    `manifest.yaml` で作成者、名前、バージョン、プラグイン種別、runner、アイコン、ソースリポジトリ、連絡先、プライバシーポリシーを正確に宣言します。

    メインの `README.md` は英語で記述します。セットアップ、使用方法、必要な API や認証情報、接続要件、ソースリポジトリを説明してください。翻訳は `readme/README_<locale>.md` に配置します。
  </Tab>
  <Tab title="依存関係">
    依存関係は最小限にし、再現可能なバージョン制約を指定します。バージョン指定のない要件、URL からの直接インストール、Git ベースのインストールは避けてください。必要な場合は PR で理由を説明します。

    Python プラグインでは `dify-plugin >= 0.9.0` が必要です。検証ツールは依存関係のメタデータを確認し、[OSV データベース](https://osv.dev/) で既知の脆弱性も照会します。
  </Tab>
</Tabs>

### プライバシーとネットワークアクセス

`PRIVACY.md` またはホストされたプライバシーポリシーには、収集、保存、記録するユーザーデータと、第三者へ送信するデータを記載します。ユーザーデータを収集しない場合も明記してください。

外部サービスへ接続する場合、想定ドメインを `manifest.yaml` で宣言できます。

```yaml
network:
  domains:
    - api.example.com
    - "*.cdn.example.com"
```

静的解析では、実行時に組み立てる URL やベンダー SDK 内部の接続先をすべて検出できません。ドメインを宣言すると、スキャナーがソースから推測できない接続先も明示できます。

## リスクの分類

該当する最も高いレベルを選択します。Marketplace の PR テンプレートでは、1 つだけ選択してください。

| レベル | 該当する場合 |
| :--- | :--- |
| **低リスク** | 固定された文書化済み HTTPS API のみを呼び出し、ユーザー制御のコード、コマンド、SQL、ファイル操作、ブラウザー自動化、任意のネットワーク要求を実行しない。 |
| **中リスク** | アップロードファイルやユーザー指定 URL を処理する、外部サービスへ書き込む、ユーザーコンテンツを外部送信する、または機密性が比較的低い個人データを処理する。 |
| **高リスク** | コードやコマンドの実行、SQL、データベースやファイルシステムへのアクセス、SSH/SFTP、ブラウザー自動化、任意 URL のプロキシやクロール、実行ファイルの同梱、機密性の高い個人データの処理を行う。 |

<Warning>
複数レベルが該当する場合は、高い方を選択します。低いラベルを選んでもレビュー範囲は狭まりません。証拠が不整合になり、レビューが遅れるだけです。
</Warning>

中リスクと高リスクのプラグインでは、セキュリティ境界を説明します。入力制約、データ送信先、使用する認証情報、タイムアウト、エラーからのシークレット漏えい防止を記載してください。

## ローカルでのビルドと検証

<Steps>
  <Step title="プラグインのパッケージ化">
    プラグインプロジェクトの 1 つ上のディレクトリで実行します。

    ```bash
    dify plugin package ./your-plugin
    ```

    `.difypkg` が生成されます。続行前に、ファイル名とサイズを確認してください。
  </Step>
  <Step title="Marketplace Toolkit のクローン">
    ```bash
    git clone https://github.com/langgenius/dify-marketplace-toolkit.git
    cd dify-marketplace-toolkit
    ```
  </Step>
  <Step title="パッケージ検証の実行">
    ```bash
    python3 validator/validate-difypkg.py /path/to/your-plugin.difypkg \
      --output-dir ./validation-report
    ```

    機密性の高い機能の検出結果と PR の開示内容を比較するには、PR 本文をファイルへ保存し、`--pr-body-file /path/to/pr-body.md` を追加します。
  </Step>
  <Step title="レポートの確認">
    `validation-report/summary.md` を開き、生成された `*.errors.txt` と `*.warnings.txt` を確認します。

    終了コード `0` は、パッケージレベルのブロッキングエラーがないことを示します。`1` は、ブロッキング項目または環境エラーの解決が必要なことを示します。警告は検証を失敗させませんが、説明を求められる場合があります。
  </Step>
</Steps>

ローカル検証では、安全な展開、パッケージ内容とサイズ、シークレットパターン、バイナリ、manifest と README のメタデータ、依存関係ポリシー、Python のコンパイルと安全性、送信先ドメイン、依存関係の脆弱性、金融活動の兆候、機密性の高い機能の開示を確認します。

<Tip>
ネットワーク接続が必要なのは脆弱性照会だけです。必要に応じて `--offline` を追加できます。この場合、レポートは依存関係を一覧表示しますが、脆弱性がないとは判定しません。
</Tip>

## CI で追加されるチェック

ローカル検証では GitHub や Marketplace のコンテキストを再現できません。提出 PR では次の内容も確認します。

- 変更された `.difypkg` が 1 つだけで、リポジトリ内のパスが正しいこと。
- PR テンプレート、タイトル、本文、リスク選択、開示が完全であること。
- 新規バージョンで、未公開であること。
- 依存関係をインストールでき、現行 daemon でプラグインをインストールできること。
- Marketplace のアップロードパイプラインをテストモードで実行できること。

<Check>
ブロッキングエラーがなく、文書と実際の動作が一致し、すべての警告を説明できれば、[Marketplace Pull Request の提出](/ja/develop-plugin/publishing/marketplace-listing/submit-plugin-to-marketplace) へ進みます。
</Check>
