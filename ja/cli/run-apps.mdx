## アプリの検索

`difyctl get console_app` を実行すると、アプリが一覧表示されます。一覧に表示されるのはサービス API アクセスがオンになっているアプリだけで、実行できるのもそれらのアプリだけです。

```bash
difyctl get console_app

# 名前の一部、mode、またはその両方で絞り込む
difyctl get console_app --name report --mode workflow
```

ほかのコマンドでは、アプリの `id` を `--app-id` として渡します。`mode` はアプリの種類を表し、アプリを実行するコマンドはこれによって決まります：

| `mode` | アプリの種類 | 実行に使うコマンド |
|:---|:---|:---|
| `workflow` | Workflow | `run console_app workflow` |
| `advanced-chat` | Chatflow | `run console_app advanced_chat` |
| `chat` | チャットボット | `run console_app chat` |
| `agent-chat` | レガシー Agent | `run console_app chat` |
| `completion` | テキストジェネレーター | `run console_app completion` |

<Info>
新しい Agent で構築したアプリは、`difyctl` では一覧表示も実行もできません。代わりに [サービス API](/ja/api-reference/guides/agent) から呼び出してください。
</Info>

## アプリの入力の確認

`difyctl describe console_app` を実行すると、アプリの変数について、名前、型、必須かどうかが表示されます。

```bash
difyctl describe console_app --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b
```

## Workflow アプリの実行

アプリの変数は、変数名をキーとする JSON にまとめ、`difyctl run console_app workflow` の `--inputs` で渡します。回答は結果の `outputs` に、出力ノードの変数をキーとして入ります。

```bash
difyctl run console_app workflow --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --inputs '{"topic": "四半期レポート"}'

# 変数をファイルから読み込む
difyctl run console_app workflow --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --inputs @inputs.json
```

<Note>
必須変数の名前を間違えると、`topic is required in input form` などのエラーで実行が失敗します。任意変数の名前を間違えた場合は、エラーにならず、その変数が省かれるだけです。変数名は [`describe console_app`](#アプリの入力の確認) で確認してください。
</Note>

## メッセージの送信またはテキストの生成

[アプリの検索](#アプリの検索) で確認したアプリの種類に対応する `run console_app` コマンドを使います。メッセージは `--query` で、変数があれば `--inputs` で渡します。テキストジェネレーターアプリが受け取るのは、通常 `--inputs` だけです。応答は結果の `text.answer` に入ります。

```bash
# チャットボットまたはレガシー Agent アプリ
difyctl run console_app chat --app-id 0a1b2c3d-4e5f-6789-abcd-ef0123456789 --query "営業時間を教えてください。"

# 変数が 1 つある Chatflow アプリ
difyctl run console_app advanced_chat --app-id 3c4d5e6f-7a8b-4c9d-8e0f-1a2b3c4d5e6f --query "今四半期は何が変わりましたか？" --inputs '{"topic": "四半期レポート"}'

# テキストジェネレーターアプリ
difyctl run console_app completion --app-id 5e6f7a8b-9c0d-4e1f-a2b3-c4d5e6f7a8b9 --inputs '{"topic": "四半期レポート"}'
```

## 会話の継続

結果の `conversation_id` を、`--conversation-id` で次の実行に渡します。

```bash
difyctl run console_app advanced_chat --app-id 3c4d5e6f-7a8b-4c9d-8e0f-1a2b3c4d5e6f --query "今四半期は何が変わりましたか？" --inputs '{"topic": "四半期レポート"}'

# 同じ会話で、同じ変数を付けて返信する
difyctl run console_app advanced_chat --app-id 3c4d5e6f-7a8b-4c9d-8e0f-1a2b3c4d5e6f --conversation-id 9f8e7d6c-5b4a-4321-8fed-cba987654321 --query "前の四半期はどうでしたか？" --inputs '{"topic": "四半期レポート"}'
```

<Note>
必須の変数は、メッセージを送るたびに渡し直してください。これらの変数を付けずに送ったメッセージは失敗します。
</Note>

Chatflow アプリの実行が停止した場合や、フォームで一時停止した場合、その結果には `conversation_id` が含まれません。停止した実行の会話は、引き続き新しいメッセージを受け付けます。こうした場合にも ID を得るには、`--stream` を付けて実行を開始してください。どのイベントにも、最上位に `conversation_id` が含まれます。

## ファイルの送信

どの実行コマンドでも、`--files` でファイル変数ごとにローカルファイルのパスを指定できます。ファイルリスト変数には、パスのリストを渡します。Web 上のファイルは、代わりに `--inputs` で渡します。各ファイル変数は、`--files` と `--inputs` のどちらか一方だけで渡してください。

```bash
difyctl run console_app workflow --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --inputs '{"topic": "四半期レポート"}' --files '{"document": "./report.pdf", "appendices": ["./q1.pdf", "./q2.pdf"]}'

# Web 上のファイル
difyctl run console_app workflow --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --inputs '{"document": {"transfer_method": "remote_url", "url": "https://example.com/report.pdf", "type": "document"}}'
```

## 時間のかかる実行の追跡

実行の進行をその場で確認するには、`--stream` を付けます。イベントが発生するたびに、1 行に 1 つの JSON オブジェクトとして出力されます。Workflow アプリの実行では、最後のイベント `workflow_finished` の `data.outputs` に結果が入ります。必要なイベントだけを出力するには、`--only` でイベント名を 1 つずつ指定します。

```bash
difyctl run console_app workflow --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --inputs '{"topic": "四半期レポート"}' --stream

# 最後のイベントだけを出力
difyctl run console_app workflow --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --inputs '{"topic": "四半期レポート"}' --stream --only workflow_finished
```

## 実行の停止

Workflow アプリまたは Chatflow アプリの実行を停止するには、その実行 ID を `difyctl stop run` に渡します。進行中の実行も、人間の入力フォームで一時停止している実行も停止できます。実行 ID は、`suspended` または `incomplete` の結果にある `run_id` です。`--stream` を付けた場合は、`workflow_started` イベントの `workflow_run_id` を使います。

チャットボット、レガシー Agent アプリ、テキストジェネレーターの応答を停止する場合は、代わりに [`stop task`](#チャットボット、レガシー-agent-アプリ、テキストジェネレーターの応答の停止) を使います。

```bash
difyctl stop run --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --run-id 4b5c6d7e-8f90-4a1b-b2c3-d4e5f6a7b8c9

# Web アプリから開始した実行など、実行 ID がない場合：進行中の実行を一覧表示する
difyctl get run --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --triggered-from app-run --status running

# フォームで一時停止している実行：--status を省き、status が paused の実行を探す
difyctl get run --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --triggered-from app-run

# status が stopped になったことを確認する（停止後しばらくは running と表示されることがある）
difyctl describe run --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --run-id 4b5c6d7e-8f90-4a1b-b2c3-d4e5f6a7b8c9
```

<Info>
Workflow アプリや Chatflow アプリの実行中に Ctrl+C を押しても、止まるのは `difyctl` だけで、サーバー上の実行は止まりません。実行も停止するには、その実行 ID を `stop run` に渡します。
</Info>

実行を停止した時点ですでに始まっているモデル呼び出しや HTTP リクエストは、最後まで処理されます。

スクリプトからは、停止と失敗は同じように見えます。両者を見分ける方法は、[実行の終了状態の確認](/ja/cli/reference/results-errors-and-exit-codes#実行の終了状態の確認) を参照してください。

## チャットボット、レガシー Agent アプリ、テキストジェネレーターの応答の停止

応答を停止できるようにするには、`--stream` を付けて開始します。そのうえで、最初のイベントにある `task_id` を `difyctl stop task` に渡します。

```bash
difyctl stop task --app-id 0a1b2c3d-4e5f-6789-abcd-ef0123456789 --task-id 26992456-d005-4add-a26d-8dff91d5f13d
```

<Note>
`stop task` は、存在しないタスク ID や、すでに終わった応答を指定しても `{"result": "success"}` と出力します。そのため、`task_id` が停止したい応答のものであることを確認し、そのストリームがまだ開いているうちに `stop task` を実行してください。

停止した応答は、最後まで終わった応答と同じように見えます。ストリームは `message_end` で終わり、応答を開始したコマンドは終了コード 0 で終了します。回答には、停止するまでに届いた内容だけが含まれます。スクリプトで回答を使う場合は、`stop task` を呼び出したことをスクリプト側で記録しておいてください。
</Note>

## 人間の入力フォームへの回答

`difyctl` からは、次の条件を満たすフォームにだけ回答できます：

- **旧バージョンの人間の入力ノード**：ノードが **Webアプリ** でフォームを配信している必要があります。
- **新しい人間の入力ノード** <Badge color="blue" size="sm">セルフホスト</Badge>：Workflow アプリが対象です。ノードの [**受信者**](/ja/self-host/use-dify/nodes/human-input#choose-who-responds) に **開始者** が含まれている必要があります。回答には、実行を開始したアカウントを使います。サインインと個人アクセストークンのどちらで認証してもかまいません。

フォームで一時停止した実行は、`status` が `suspended` の結果を返します。フォームに回答できる場合、結果にはアクションボタンごとにヒントが 1 つずつ含まれます。フォームがほかの受信者にだけ送られた場合、`hints` は `[]` になり、そのうちの誰かが回答すると実行が再開します。

回答するには、選んだアクションのヒントにある `inputs` の各 `null` を回答に置き換えて、[そのヒントを実行](/ja/cli/find-and-run-commands#ヒントの活用) します。先にフォームのフィールドを確認するには、いずれかのヒントから `form_token` を取得して `difyctl describe run form` を実行します。その後、`submit run form` で回答します。

新しいノードでは、送信する前に、`inputs` が `describe run form` の内容に合っているかを確認してください：

- すべてのフィールドに値を入れ、`null` を残さない。
- 段落フィールドには文字列を、選択フィールドにはその選択肢のいずれかを指定する。
- キーには、フォームのフィールドだけを使う。

`inputs` がこれらのいずれかに反していると、`submit run form` は `invalid_input` で失敗します。

誰が回答した場合も、再開した実行は `get run event` で追跡します。その際、一時停止時に返された結果の `run_id` を `--run-id` に指定します。`--include-state-snapshot` は省略しないでください。省略すると、コマンドが最大 5 分間何も出力しないことがあります。

```bash
# フォームのフィールドを表示する
difyctl describe run form --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --form-token Xq7Lm2RtPz9KcV4bN8wJdE

# アクションを指定して送信する。フォームにフィールドがない場合は --inputs '{}' を指定する
difyctl submit run form --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --form-token Xq7Lm2RtPz9KcV4bN8wJdE --action approve --inputs '{"comment": "問題ありません"}'

# 再開した実行を追跡する
difyctl get run event --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --run-id 4b5c6d7e-8f90-4a1b-b2c3-d4e5f6a7b8c9 --include-state-snapshot

# 実行が後で別のフォームで再び一時停止する可能性がある場合は、追跡を続ける
difyctl get run event --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --run-id 4b5c6d7e-8f90-4a1b-b2c3-d4e5f6a7b8c9 --include-state-snapshot --continue-on-pause
```

<Info>
新しいノードでは、同じフォームがメールや IM（インスタントメッセージングアプリ）でも届くことがあります。どの経路で届いたフォームでも、最初の回答だけが有効です。それ以降に `submit run form` を実行しても失敗します。
</Info>

## 実行が失敗した原因の調査

Workflow アプリまたは Chatflow アプリの実行では、失敗した結果の `run_id` から調べ始めます。または、`difyctl get run` で失敗した実行を一覧表示します。次に、`describe run` で実行を、`get run node` でそのノードを確認します。

```bash
difyctl get run --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --triggered-from app-run --status failed

# 実行の入力、出力、ステータス、エラー
difyctl describe run --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --run-id 4b5c6d7e-8f90-4a1b-b2c3-d4e5f6a7b8c9

# 各ノード。失敗したノードにエラーが含まれる
difyctl get run node --app-id 7f3e9a2b-1c4d-4e8f-9a0b-2d5c8e1f4a7b --run-id 4b5c6d7e-8f90-4a1b-b2c3-d4e5f6a7b8c9
```

<Note>
`--triggered-from app-run` は省略しないでください。省略すると、ドラフトのテスト実行しか一覧に表示されません。
</Note>

## トラブルシューティング

| メッセージ | 対処方法 |
|:--|:--|
| `invalid run input`（入力に誤りがない場合） | アプリが一度も公開されていない可能性がある。公開してから、もう一度実行する。 |
| `unknown flag "--task-id"`（`stop run` または `get run event` の場合） | 代わりに `--run-id` で、結果の `run_id` などの実行 ID を渡す。チャットボット、レガシー Agent アプリ、テキストジェネレーターの応答を `task_id` で停止するには、[`stop task`](#チャットボット、レガシー-agent-アプリ、テキストジェネレーターの応答の停止) を使う。 |
| `run_not_found` | `task_id` ではなく実行 ID を渡しているか、`--app-id` に実行が属するアプリを指定しているかを確認する。 |
| `run_not_stoppable` | まず `describe run` で実行の状態を確認する。すでに終了していれば、停止する必要はない。<br/><br/>まだ進行中か、フォームで一時停止している場合、その実行はサーバーのアップグレード前に開始されている。自分のアカウントで開始した実行（`difyctl` からの開始やテスト実行）がフォームで一時停止している場合は、`get run event` を一度実行する。その際、実行 ID と `--include-state-snapshot` を指定する。そのあと、`stop run` をやり直す。それ以外の実行は `difyctl` からは停止できない。 |
| `app_mode_mismatch`（`stop run` または `stop task` の場合） | Workflow アプリや Chatflow アプリの実行は `stop run` で、ほかのアプリの応答は [`stop task`](#チャットボット、レガシー-agent-アプリ、テキストジェネレーターの応答の停止) で停止する。 |
| `form_not_found` | メールや IM のリンクにあるトークンではなく、一時停止時に返された結果の `hints` にある `form_token` を渡しているかを確認する。あわせて、`--app-id` に実行が属するアプリを指定しているかも確認する。新しいノードでは、実行を開始したアカウントしか回答できない。 |
| `already_submitted` または `human_input_form_submitted` | フォームにはすでに回答がある。ほかの受信者が回答したか、メールや IM で自分に届いたリクエストから回答したか、以前に送信済みかのいずれか。実行はその最初の回答で進む。`get run event` で追跡する。 |
| `expired` または `human_input_form_expired` | 回答がないままフォームがタイムアウトしたか、実行が停止された。`describe run` で、実行がどう終わったか、またはどう続いたかを確認する。 |

どのコマンドでも起こりうるエラーについては、「結果、エラー、終了コード」の [トラブルシューティング](/ja/cli/reference/results-errors-and-exit-codes#トラブルシューティング) を参照してください。
