### Phoenix 简介

[Arize Phoenix](https://arize.com/phoenix/) 是 [Arize AI](https://arize.com/?utm_source=dify-docs&utm_medium=partner&utm_campaign=partner-docs&utm_content=integrate-phoenix-self-host) 推出的开源平台，基于 OpenTelemetry 构建，为 LLM 工作流和 Agent 提供可观测性、评估、提示工程和实验能力。

开发阶段可在本地运行 Phoenix，也可在自有基础设施上以单容器方式自部署，或使用 Arize 托管的 [Phoenix Cloud](#配置-phoenix-cloud)。

如需面向生产环境团队、AI 原生公司和企业的全功能平台，可改用 [Arize 集成](/zh/self-host/use-dify/monitor/integrations/integrate-arize) 接入 [Arize AX](https://arize.com/products/ax/)。

追踪数据接入后，可参考 Arize 的 [Agent 评估指南](https://arize.com/ai-agents/agent-evaluation/) 和 [LLM 评估指南](https://arize.com/resources/llm-evaluation/)，了解如何用追踪数据调试故障、评估 Agent 行为、监控模型质量。

### 配置 Phoenix

本章节将指引你注册 Phoenix 并将其集成至 Dify 平台内。

如果自部署的 Phoenix 实例未启用身份验证，可跳过以下账户和 API 密钥步骤，并将 **API Key** 留空。

#### 1. 注册/登录 [Phoenix](https://app.arize.com/auth/phoenix/signup)

### 2. 获取 Phoenix API 密钥

从右上角的用户菜单中获取 Phoenix API 密钥。点击 **API Key**，然后点击 API Key 进行复制：

<Frame>
  ![](https://i.ibb.co/pB1W0pk8/dify-docs-phoenix-api-key.png)
</Frame>

### 3. 集成 Phoenix 与 Dify

在 Dify 应用中配置 Phoenix。打开需要监控的应用，在侧边菜单中打开 **监控**，并在页面上选择 **追踪应用性能**。

<Frame>
  ![](https://i.ibb.co/gMmXxfhQ/dify-docs-phoenix-in-use.png)
</Frame>

<Frame>
  ![](https://i.ibb.co/jv6QFbp7/dify-docs-phoenix-config.png)

成功保存后，你可以在当前页面查看监控状态。

<Note>
保存配置并启用追踪后，重新运行应用，在监控服务中确认是否出现新的追踪记录。追踪数据会异步发送，仅保存配置不能确认追踪数据已送达。

当两个部署开关均关闭时，新版 Agent 应用及使用 [新版 Agent 节点](/zh/self-host/use-dify/nodes/agent#new-agent) 的工作流仍会发送常规追踪，包括可用的输入和输出，但不包含 Agent 内部的模型和工具调用。

要采集这些调用，请在 Dify API 和 worker 上启用 `OPS_AGENT_TRACE_ENABLED=true`，并在 Agent 后端启用 `DIFY_AGENT_APPLICATION_TRACING_ENABLED=true`。两个开关需要同时启用：如果只启用 API 开关，且 **采集 Agent 内部过程** 保持开启（默认），执行 Agent 调用时追踪采集会超时，报出 `agent_trace_collection_incomplete`，并且不会导出追踪。这不代表应用执行失败。部署设置详见 [环境变量](/zh/self-host/deploy/configuration/environments#llmops-追踪投递)。

为这些应用启用 API 采集后，**采集内容** 默认关闭：整个工作流的输入、输出和大部分元数据会被移除，错误文本也会被脱敏。开启该设置后才会发送这些内容。经典 `agent-chat` 应用和仅使用经典 Agent 节点的工作流仍使用常规追踪。
</Note>

## 监控数据列表

以下数据说明适用于常规追踪。为新版 Agent 应用或包含新版 Agent 节点的工作流启用 API 采集后，追踪会使用新的 UUIDv7 追踪 ID，源 ID 和追踪运行 ID 则保留在 `dify.source.id` 和 `dify.tracing.run_id` 属性中。对于新版 Agent 应用，开启 **采集 Agent 内部过程** 后，包含内部模型和工具调用的 `Agent attempt` span 会替代常规 `llm` span。通过此方式采集的运行不会单独导出审核、建议问题和命名记录。

Dify 会按父子层级导出执行操作：消息包含 `llm` 调用，Chatflow 消息包含工作流及其节点操作。对于消息 ID、工作流运行 ID 或调用方传入的 ID，追踪 ID 会保留非零 UUID 或 32 位十六进制 ID 的值，其他值则通过哈希转换。span ID 通过派生生成。提供的 `X-Trace-Id` 优先于消息 ID 或工作流运行 ID。只有模型调用会填充监控服务的原生 token 用量字段。

每个 span 的 `user.id` 优先使用 `end_user_session_id`，不可用时使用 `user_id`。独立的 `metadata.user_id` 字段仍保留 Dify 用户记录的 ID。

以下明细列出 Dify 的源记录和元数据。实际导出时仅发送相关且可用的值，不会完整发送原始记录。
