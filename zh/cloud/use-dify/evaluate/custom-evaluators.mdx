[内置指标](/zh/cloud/use-dify/evaluate/metrics) 回答的是通用问题，例如回答是否有据可依、是否与参考答案一致。如果要检查你自己的规则，例如规定的格式、长度上限，或你用自己的话写下的评分标准，可构建自定义评测器。

自定义评测器可用 LLM 节点按你的评分标准打分，也可用代码执行节点做精确检查，或两者兼用。它的输出和内置指标的用法一样，判定条件可据此决定各行是否通过。

<Info>
自定义评测器仅适用于对 Workflow 应用和 [Snippet](/zh/cloud/use-dify/build/snippet) 的评测。
</Info>

下文用一个示例贯穿始终：搭建一个评测器，按团队的风格规范检查客服工作流的回答。

<Tip>

## 自定义评测器的工作原理

自定义评测器是一个发布为评测工作流的 Workflow 应用。评测时，测试集的每一行都会运行它一次。

评测器的用户输入节点接收的值由你选定，取自被评测的工作流在该行的那次运行：可以是输入变量（如问题），也可以是某个节点的输出（如回答）。评测器读不到测试集中的参考答案，要和参考答案比对，交给内置指标即可。

评测器输出节点中的每个变量，都会作为该行的一个自定义指标返回。

一次评测只能使用一个自定义评测器。要检查多条规则，就把它们都放进同一个评测器；需要单独判定的规则，各配一个输出。

评测器的运行就是它所在应用的普通运行，会出现在该应用的 **日志** 中，每处理一行就多一条。如果模型使用的是你的 [AI 消息额度](/zh/cloud/use-dify/workspace/model-providers#使用-ai-消息额度调用模型)，这些调用也从额度中扣除。

## 搭建评测器

假设你的客服工作流接收一个 `question`，从知识库中检索相关段落，再由 LLM 节点根据这些段落作答。团队希望每个回答都符合以下风格：答的是用户实际问的问题，篇幅控制在 200 字左右，并在结尾给出用户可采取的下一步操作。

要检查这些规则，新建一个 Workflow 应用，命名为 `Support Style Check`。评测工作流不能包含触发器节点或人工介入节点，因此不要添加这两类节点。

### 接收要检查的值

在用户输入节点中，为评测器要接收的每个值各添加一个输入变量。要判断回答是否回应了问题，评测器需要同时拿到问题和回答，因此添加两个段落类型的变量：`question` 和 `answer`。

### 按规则为回答打分

根据规则选择打分节点：

- 需要判断力的规则，例如回答是否回应了问题，要用一个写有评分标准的 LLM 节点。
- 脚本能精确检查的规则，例如字数或某个必须出现的值，适合用代码执行节点。

本例的长度限制只是个大概，因此一个 LLM 节点就能判断全部三条规则。

添加一个名为 `Style Check` 的 LLM 节点，将温度设为 0，因为打分节点对同一个回答每次都应给出相同的分数。在它的系统指令中写明规则，以及每种结果对应的分数：

```text wrap
你负责按照以下三条风格规则审核一条客服回答：
1. 回答了用户实际提出的问题。
2. 篇幅不超过 200 字左右。
3. 结尾给出了用户可采取的下一步操作。

给出 0 到 1 之间的分数：三条规则都满足得 1 分，满足两条得 0.67 分，满足一条得 0.33 分，都不满足得 0 分。
用一句话说明理由，指出回答违反了哪条规则。
```

为每种结果写明分数后，违反同一条规则的两个回答就会得到相同的分数。在结果中看那一句理由，就知道回答违反了哪条规则。

在 User 消息中插入这两个输入变量：

```text
问题：{{question}}
回答：{{answer}}
```

### 返回可供条件检验的分数

每个输出都会成为一个指标，判定条件如何检验，取决于输出的类型：

- **数值**（整数或小数），例如 `score`：与阈值比较，例如 ≥ 0.8
- **布尔**，例如 `passed` 标记：检验是真还是假
- **文本**，例如 `reason`，以及其他任何类型：按文本比较，例如用「包含」

要为分数设定阈值，分数就必须是数值。回到 `Style Check`，开启 [结构化输出](/zh/cloud/use-dify/nodes/llm#结构化输出)，并添加两个必填字段：

| 字段 | 类型 | 描述 |
|:------|:-----|:------------|
| `score` | number | 0 到 1 之间的分数 |
| `reason` | string | 一句话理由 |

然后将这两个字段添加到 [输出](/zh/cloud/use-dify/nodes/output) 节点：

- `score`：取自 `Style Check` 的 `structured_output.score`
- `reason`：取自 `Style Check` 的 `structured_output.reason`

## 发布为评测工作流

在编辑器中，用一组示例问题和回答运行一次评测器。如果返回的 `score` 和 `reason` 看起来没问题，打开 **发布** 菜单，点击 **发布为评测工作流**。

要把已经发布的工作流变成评测器，则选择 **切换为评测工作流**。它转换的是当前已发布的版本，所以草稿里的改动要先发布。

评测工作流可切换回标准工作流，但在它重新成为评测工作流之前，用到它的评测都无法运行。

## 添加到评测

打开客服工作流的 **评测** 页面，点击 **添加指标** > **自定义指标**，然后选择 `Support Style Check`。

在 **变量映射** 下，为评测器的每个输入变量选定取值，这些值来自客服工作流的已发布版本：

- `question`：取自用户输入节点的 `question`
- `answer`：取自 LLM 节点的 `text`，即回答本身

如果被评测的工作流有分支，应从每条路径都会运行的节点映射。如果不同分支由不同节点给出回答，先用 [变量聚合器](/zh/cloud/use-dify/nodes/variable-aggregator) 节点把它们合并，再从该节点映射。

## 根据输出判定通过与否

在 **判定条件** 下，添加条件 `Support Style Check / score` ≥ 0.8。违反任意一条风格规则的回答，得分都低于 0.8，因此只有全部遵守的回答才能通过。

自定义指标和内置指标可在同一组条件中组合使用。假设这次评测还用 Faithfulness 为 LLM 节点打分，那就再添加 Faithfulness ≥ 0.8，并用 **且** 连接这两个条件。

## 更新或删除评测器

- **更新规则**：编辑评测器并发布。更新只对之后发起的运行生效。

- **删除评测器**：先确认用到它的运行都已结束，因为删除会取消其中仍在进行的运行。删除后，评测器会从各个评测中移除，为它的输出设置的条件也会一并删除。如果某个评测除它之外没有其他指标，这个评测保存的整套配置都会丢失。

## 评测器在某一行失败时

某一行显示 `EVAL_CUSTOM_EVALUATOR_FAILED`，通常是以下原因之一：

- **该行缺少某个映射值**：提供该值的节点没有运行，或没有输出你映射的字段。如果是分支跳过了该节点，改为从每条路径都会运行的节点映射。

- **映射值与评测器的输入变量不匹配**：例如值不是文本，或文本超出了变量的长度限制。这时评测器不会运行，它的日志里也就没有记录。对照每个变量的类型和长度限制，逐一检查映射。

- **评测器运行失败**：例如模型调用出错。在评测器应用的 [日志](/zh/cloud/use-dify/monitor/logs) 中找到这次运行，查看出了什么问题。

- **评测器的创建者已离开工作空间**：评测器以创建者的身份运行，因此每一行都会失败。请一位现有成员新建一个评测器，发布为评测工作流，再在评测中用它替换旧的评测器。
